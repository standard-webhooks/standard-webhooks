# Webhook endpoint verification

Webhook endpoint verification (WEV) is a way for a webhook producer to confirm that an endpoint is willing and able to receive its webhooks. The producer includes a random challenge in a request to the endpoint, and the endpoint responds with a value that can only be calculated by someone who holds the endpoint's key: the signing secret for symmetric signatures, or the public key for asymmetric ones. Similar schemes are commonly known as a challenge-response check (CRC).

Most webhook producers don't need endpoint verification, as for most of them the benefits don't justify the extra friction. It can also be added later, for all newly created endpoints, if these issues ever become a problem.

If you do need endpoint verification, this extension provides a standard way of doing it.

## Goals

Webhook producers usually let consumers register any URL they want, and then send requests to it. Endpoint verification is meant to achieve the following goals:

- Consent: make sure that whoever operates the URL has opted in to receiving the webhooks. Without endpoint verification, anyone can register a URL they don't control, and use the producer to flood it with requests.
- Correct configuration: make sure the consumer holds the correct key before any webhooks are delivered. A very common failure mode is an endpoint that is deployed with the wrong key, or without one at all.

Non-goal: endpoint verification is not meant to prove that the consumer verifies the signature of every webhook it receives.

### Why not just echo the challenge

A common and simpler approach is to have the endpoint respond with the challenge it received. This is better than nothing, but it has two weaknesses:

1. It doesn't prove that the consumer has the correct key. An endpoint can echo the challenge without having a key configured at all.
2. It doesn't prove consent. An endpoint that echoes challenges will do so for anyone, not only for the producer it was set up for. So an attacker that knows the URL of an existing endpoint can register it with another account of the same producer, or with an entirely different producer that uses the same kind of check, and it will pass. Any URL that can be made to echo back part of the request will pass as well.

The scheme below solves both by requiring the consumer to sign the challenge using a key derived from the endpoint's key. Since keys are unique per endpoint, an endpoint can only respond correctly to checks for its own registration. Registering the same URL again, with another account or a different producer, results in a different key that the endpoint doesn't hold.

## How it works

### The challenge

The producer requests endpoint verification by including the `webhook-challenge` header in a dedicated `POST` request to the endpoint. This specification doesn't dictate the body of the request.

The request should be signed like any other webhook (with the `webhook-id`, `webhook-timestamp` and `webhook-signature` headers), so that it passes through any verification the consumer already has in place. However, verifying it before responding to the challenge is not required, and is up to the consumer.

For example:

```
webhook-challenge: 0njH7N3kV5eXPB+/eh+eoA2Ahvz2JgNp0iC/BLOl6yM=
```

The challenge should be 32 random bytes generated by a cryptographically secure random number generator, base64 encoded. A new challenge must be generated for every request.

### Calculating the response

The consumer calculates the response as follows:

```
// A separate key domain: the verification key is only ever used for endpoint verification responses.
verification_key = HMAC-SHA256(key=endpoint_key, msg="wev-v1")

signature = base64(HMAC-SHA256(key=verification_key, msg=challenge))
```

Where `challenge` is the value of the `webhook-challenge` header exactly as received (the base64 string itself, not the decoded bytes), and `endpoint_key` depends on the type of signature used by the endpoint:

|                      | Symmetric                                                     | Asymmetric                                                       |
| -------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------- |
| `endpoint_key`       | The raw secret bytes (the base64 decoded part after `whsec_`) | The raw public key bytes (the base64 decoded part after `whpk_`) |
| Signature identifier | `v1`                                                          | `v1a`                                                            |

In both cases these are the same bytes the consumer already uses for verifying webhooks, so no additional configuration is needed.

The `wev-v1` label can never collide with the content of a webhook signature, as the signed content of a webhook (`msg_id.timestamp.payload`) always includes at least two `.` characters, and the label includes none.

The consumer then includes the `webhook-challenge-response` header, set to the signature calculated above prefixed with the signature identifier, in its response. For example:

```
webhook-challenge-response: v1,2WoO4Z1kjgoudcvk4PX/8LDD6FNJDEUHMtYqZpNx/FA=
```

The response body is ignored.

Unlike the `webhook-signature` header, `webhook-challenge-response` contains a single signature, calculated with the key the consumer holds. A consumer that holds more than one key (e.g. in the middle of a key rotation) should use the newest one. It's the producer, which knows all of the endpoint's active keys, that checks the response against each of them.

Libraries implementing this extension should expose a function that takes the challenge and returns the value of the `webhook-challenge-response` header, so that consumers don't need to implement the scheme themselves. For example:

```
const challenge = request.headers["webhook-challenge"]
if (challenge) {
  response.headers["webhook-challenge-response"] = wh.endpointVerificationResponse(challenge)
}
```

### Verifying the response

The producer considers the check successful if the response has a `2xx` status code, and the `webhook-challenge-response` header matches the expected value calculated with one of the endpoint's currently active keys.

Any other response, including a timeout, is considered a failure. Redirects must not be followed, as the response has to come from the registered URL itself.

Producers should compare the whole header value, including the signature identifier, in constant time. Anything other than a single matching signature (e.g. a list of signatures, or an unknown identifier) is a failure.

Libraries implementing this extension should also expose a function that verifies the `webhook-challenge-response` header against the challenge that was sent. Producers with multiple active keys call it once for each key. For example:

```
const header = response.headers["webhook-challenge-response"]
try {
  wh.verifyEndpointVerificationResponse(challenge, header)
} catch (e) {
  // The check failed: pause the endpoint
}
```

### When to verify an endpoint

- When an endpoint is created: since the key is usually generated by the producer when the endpoint is created, the consumer often can't respond correctly at that point. Endpoints should therefore start in a paused (unverified) state, and consumers should be able to trigger the check (e.g. through the API or the dashboard) once their endpoint is deployed. Real webhooks must not be delivered to an unverified endpoint.
- When the endpoint URL changes: the new URL may be operated by someone else entirely, so the endpoint should be paused again until the new URL passes the check.
- Periodically (optional): this confirms the endpoint is still willing to receive webhooks.

When a check triggered by endpoint creation or a URL change fails, the endpoint stays paused until it passes a check.

When a periodic check fails, the producer should pause deliveries to the endpoint. Since the failure may just be a temporary outage, the producer should keep retrying the check following a retry schedule similar to the one used for [deliveries](../standard-webhooks.md#deliverability-and-reliability), and resume deliveries once it passes. Webhooks triggered while the endpoint is paused should be kept and delivered once it resumes, rather than dropped.

Producers should notify the consumer through other channels (e.g. email) whenever an endpoint is paused due to a failed check.

## Additional notes

- Endpoint verification uses a separate key domain (derived from the key using `wev-v1`) so that it doesn't expose a signing oracle signing attacker-chosen data. This is also why consumers don't have to verify the request before responding to the challenge: the response isn't useful for anything other than passing endpoint verification for this endpoint.
- Asymmetric keys: anyone who knows the public key can calculate the response, and that's fine. The goals are met by the endpoint itself calculating it, which shows that its operator configured this specific key, and since keys are unique per endpoint, it can't be used to pass checks for anyone else's registration.
- Headers only: the challenge and the response are deliberately passed in headers, so the verification request can have whatever body the producer wants, and the consumer can respond with whatever body it wants.
